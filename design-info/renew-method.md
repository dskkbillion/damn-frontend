# Flutter Clean Architecture 增量重构方法论
**版本**: 1.3
**日期**: 2025年4月1日

## 1. 概述
本方法论旨在为 `DSKK-Flutter` 项目（或其他类似的大型 Flutter 应用）从现有代码库（如 React Native）重构至基于 `Clean Architecture` 的 Flutter 应用提供一套结构化、系统化的指导方案。其核心目标是有效管理重构过程中的复杂性，特别是降低认知负担、解耦模块、提高代码质量、可维护性、可测试性和开发效率，同时确保项目进度可控、可见。

## 2. 核心原则与组成部分
### 2.1. 目标架构 (Target Architecture)
*   **框架**: Flutter
*   **架构模式**: `Clean Architecture` (严格分层：Presentation, Domain, Data)
*   **状态管理**: `Bloc` (或团队选定的、与分层兼容的状态管理方案，如 `Riverpod`)
*   **模块化**: 按业务能力/功能划分模块 (例如: `Auth`, `Home`, `Orders`, `Profile`, `Chat`, `AI_Docs`, `Seller` 等)

### 2.2. 开发策略 (Development Strategy)
*   **增量式 (Incremental)**: 项目通过一系列小的、可管理的步骤逐步完成重构，避免"大爆炸"式修改。
*   **模块聚焦 (Module-Focused)**: 一次只深入重构一个模块。将复杂问题分解，集中精力解决，是应对认知负担的核心策略。
*   **接口先行 (Interface-First)**: 在重构模块前或过程中，优先梳理和定义其 `Domain` 层的接口（`Use Cases`, `Repository Interfaces`），明确模块的职责、能力和对外的契约。

### 2.3. 信息来源 (Information Source)
**将现有代码库 (如 RN) 作为参考**:
*   视为详细的业务需求规格和逻辑参考。
*   用于确认功能范围、验证模块划分。
*   用于理解核心业务逻辑（以便用 Dart 和 `Clean Architecture` 重写）。
*   用于明确数据结构和 API 交互细节（以实现 Flutter `Data` 层）。
*   用于梳理 UI 流程和用户交互（以设计 Flutter `Presentation` 层）。

**警惕陷阱**:
*   避免直接复制代码或结构。 目标是构建高质量、符合 Flutter 和 `Clean Architecture` 范式的代码。
*   主动识别并改进参考代码中可能存在的"坏味道"（如耦合、逻辑混乱）。

### 2.4. 边界定义与解耦 (Boundary Definition & Decoupling)
*   **围绕"业务能力"定义边界**: 模块的核心是其提供的独特业务价值。
*   **`Domain` 层接口是契约**:
    *   模块间的业务逻辑交互通过依赖对方模块 `Domain` 层定义的接口实现（推荐使用依赖注入）。
*   **中央路由服务**:
    *   跨模块的页面导航通过调用一个共享的、基于逻辑路径（而非具体 Widget）的导航服务实现。
*   **严格依赖规则**:
    *   遵循 `Clean Architecture` 的依赖方向 (`Presentation` -> `Domain` <- `Data`)。
    *   模块间依赖优先（理想情况是仅）发生在 `Domain` 层接口层面。

### 2.5. 隔离与验证 (Isolation & Verification)
*   **依赖模拟 (Mocking)**:
    *   在开发、测试、预览单个模块时，大量使用 Mock 技术模拟其外部依赖（其他模块的接口实现、导航服务的返回、`Data` 层的 API 响应等）。这是实现模块独立开发和测试的关键。
*   **单元/Widget 测试**:
    *   在模块重构过程中，为其编写或完善单元测试（重点是 `Domain` 层逻辑和 `Presentation` 层 `Bloc/Cubit`）和 Widget 测试（`Presentation` 层 UI 交互）。
    *   设定明确的测试覆盖率目标，作为模块"完成"标准的一部分。
*   **模块预览环境 (Module Preview Environment)**:
    *   搭建一个可以独立运行和交互当前正在重构模块（的关键页面/流程）的环境。
    *   该环境应能方便地注入 Mock 依赖。
    *   **目的**：快速验证 UI 和基本流程，提供可见的进度反馈，降低完整集成后的调试成本。

### 2.7. LLM 辅助 (Optional but Recommended)
*   **定位**: 将大模型（LLM）视为高效助手，而非项目主导。
*   **应用场景**:
    *   代码生成（基于接口的模板代码、测试代码、Mock 代码）。
    *   代码解释、注释和文档生成。
    *   特定技术点的实现方案建议。
    *   小范围、明确目标的代码重构建议。
*   **决策权**: 人类开发者负责架构设计、边界定义、复杂逻辑实现和最终的技术决策。

## 3. 主工程初始化与准备
在开始进行第一个模块的重构循环之前，需要搭建一个基础的"主工程"框架。这是所有模块最终集成的目标环境，并提供必要的共享基础设施。

**主要任务包括**：
*   **创建项目结构**:
    *   使用 `flutter create` 创建项目。
    *   建立顶层目录结构，例如 `lib/features` (或 `modules`) 用于存放功能模块，`lib/core` (或 `shared`) 用于存放共享代码。
*   **配置核心依赖**:
    *   在 `pubspec.yaml` 中添加并配置核心库：Flutter SDK, 状态管理库 (`Bloc`, `Riverpod` 等), 依赖注入库 (如 `get_it`, `provider`), 导航库 (如 `go_router`, `auto_route`)。
*   **设置应用入口**:
    *   创建最小化的 `main.dart`，初始化必要的服务（如 DI, 导航），并运行 `runApp()` 启动根 Widget (如 `MaterialApp`)。
*   **初始化导航服务**:
    *   配置并初始化所选的中央路由库，建立导航机制，即使初期路由表为空或只有根路由。
*   **初始化依赖注入**:
    *   配置并初始化依赖注入容器，建立 DI 机制。
*   **（可选）建立 Core/Shared 模块**:
    *   创建 `core` 或 `shared` 模块，用于放置应用级共享内容：基础主题 (`ThemeData`), 全局常量, 日志封装, 基础网络客户端配置等。
*   **确保可运行**:
    *   验证这个基础的"空壳"应用能够成功构建和运行。

## 4. 核心工作流 (针对单个模块的重构循环)
1.  **选择模块**: 根据优先级（如：依赖少、核心模块、问题最多）选择当前要重构的模块。
2.  **定义模块边界**: 明确模块核心业务能力，识别用例(`Use Cases`)、核心实体(`Entities`)和所需仓库接口(`Repository Interfaces`)。分析并初步定义与其他模块的交互点（依赖接口、导航需求）。(这是关键的设计步骤)
3.  **分析参考代码 (验证与细化)**: 深入研究参考代码，验证已定义的边界，并提取实现所需细节。此步骤的产出（形式灵活，如笔记、注释、列表、代码片段等）应至少覆盖：
    *   **边界验证**: 确认或调整记录（对比 RN 实现与步骤 2 定义的 `Use Case`/`Entity`/`Repo Interface` 是否匹配）。
    *   **业务逻辑 (`Domain` 层)**: 具体算法、计算规则、验证逻辑、状态流转条件、关键决策逻辑。
    *   **数据交互 (`Data` 层)**: API 端点、请求/响应格式（含示例）、认证方式、数据库/本地存储细节、底层错误处理模式。
    *   **UI 流程与交互 (`Presentation` 层)**: 页面导航序列、关键 UI 元素及其所需状态、用户事件到 `Use Case`/导航的映射、表单验证规则。
4.  **精化 `Domain` 层接口**: 基于边界定义和参考代码分析，最终确定并完善 `Domain` 层的 `Entities`, `Use Cases`, `Repository Interfaces` 及其详细契约。（把接口定义（包括详细的参数、返回值、错误类型注释）写在 Dart 代码（`.dart` 文件）中）
5.  **实现 Flutter `Data` 层**: 实现 `Repository Interface`，创建 `Data Sources`（包括用于测试和预览的 `Mock DataSource`），定义 `DTOs`。
6.  **实现 Flutter `Domain` 逻辑**: 实现 `Use Cases`，包含核心业务规则。
7.  **实现 Flutter `Presentation` 层**: 创建 `Widgets/Pages`，实现 `Blocs/Cubits` (或 `Riverpod Providers`)，确保其依赖 `Domain` 层的 `Use Case` 接口。（实现的时候，布局可以参考原型设计）
8.  **识别并配置外部依赖**:
    *   确定需要调用的导航服务方法。
    *   确定需要依赖的其他模块 `Domain` 接口，并在依赖注入配置中暂时注入 `Mock` 实现。
9.  **编写单元/Widget 测试**: 覆盖 `Domain` 层逻辑、状态管理逻辑 (`Bloc`/`Riverpod`) 和关键的 `Widget` 交互。
10. **在模块预览环境中调试和验证**: 运行模块的独立预览，交互测试，确保在隔离环境下工作正常。
11. **(模块完成后) 集成准备**: 准备将模块代码合并回主工程。（详见第 5 节）
12. **执行集成与测试**: 将模块合并，配置真实依赖，并执行集成测试。（详见第 5 节）
13. **重复**: 选择下一个模块，开始新的循环。

## 5. 模块集成流程详解
本节详细阐述核心工作流中的步骤 11 和 12，即如何将独立重构完成的模块安全、有效地集成回主工程。

### 5.1. 前提条件 (Prerequisites)
*   **满足"完成"定义 (DoD)**: 确保模块已达到预定义的完成标准（代码质量、测试覆盖率、预览验证通过等）。
*   **代码评审通过**: 模块代码已通过 Pull Request / Merge Request 评审。
*   **主开发分支为最新**: 确保用于合并的本地主开发分支（如 `develop`）已更新到最新。

### 5.2. 代码合并 (Code Merging)
*   **使用 Git**:
    *   切换到主开发分支 (`git checkout develop`)。
    *   从模块的特性分支（如 `feature/refactor-orders-module`）合并代码 (`git merge feature/refactor-orders-module --no-ff` 或使用 Rebase 策略）。
    *   解决可能出现的合并冲突。
*   **代码结构**: 合并操作会将新模块的代码（或替换后的代码）放入主工程的相应目录（如 `lib/features/orders`）。

### 5.3. 配置更新 (Configuration Updates - 在主工程中)
*   **依赖注入 (DI)**:
    *   修改主工程的 DI 配置文件。
    *   将与该模块相关的 Mock 依赖替换为真实实现（如注册 `OrderRepositoryImpl`）。
    *   配置应用其他部分对该模块新提供服务的依赖。
*   **导航 (Navigation)**:
    *   修改主工程的中央路由配置。
    *   注册由新模块提供的页面路由，使其可通过逻辑路径访问。

### 5.4. 集成测试 (Integration Testing - 关键步骤)
*   **目的**: 验证模块在真实依赖和导航环境下，能否与主工程的其他部分正确协作。
*   **测试类型**:
    *   模块间交互测试: 编写测试用例验证跨模块调用的正确性。
    *   端到端 (E2E) 测试: 运行覆盖该模块关键流程的用户场景测试。
    *   回归测试: 确保此次集成没有破坏应用的其他现有功能。
*   **执行**: 在合并和配置更新后，立即运行所有相关的集成测试套件。

### 5.5. 管理策略 (Management Strategies)
*   **分阶段集成**: 优先选择一次集成一个模块，稳定后再集成下一个，降低风险。
*   **沟通协调**: 团队内清晰沟通集成计划、进度和结果。
*   **回滚计划**: 熟悉使用 Git 回滚合并操作的方法，以备出现严重问题时使用。
*   **持续集成 (CI)**: 利用 CI 工具在每次合并后自动运行构建和测试，快速反馈问题。
