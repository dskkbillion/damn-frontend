# 项目缓存与本地存储策略

## 1. 引言

本文档旨在为 DSKK Flutter 项目定义一套统一的缓存和本地存储策略。目标是提升应用性能、改善用户体验（特别是在网络不稳定或离线情况下）、减少不必要的网络请求，并为团队成员在技术选型和功能实现上提供明确指引。策略的设计依据是各模块边界定义文档 (`docs/BD/`) 中明确的核心业务需求和数据特性。

## 2. 指导原则

*   **分层负责**: 缓存和本地存储逻辑主要封装在 **数据层 (Data Layer)** 的 `RepositoryImpl` 实现类中。领域层 (Domain Layer) 的 Use Cases 和表示层 (Presentation Layer) 的 Blocs/Cubits 不应直接关心数据是来自缓存、本地存储还是网络。
*   **数据一致性**: 必须有明确的缓存失效和数据同步机制，以确保用户看到的数据尽可能准确。
*   **用户体验优先**: 在保证数据基本准确的前提下，优先从缓存或本地存储加载数据，以提高界面响应速度。后台可以异步获取最新数据并更新界面。
*   **区分场景**: 明确区分**缓存 (Caching)**（临时存储，提高访问速度）和**本地存储 (Local Storage)**（持久化存储，用于离线数据、草稿等）。
*   **安全性**: 敏感数据（如认证 Token）必须使用安全存储。
*   **错误处理**: 健壮地处理缓存/存储读取失败、写入失败、同步失败等情况，通常应回退到网络请求或向用户显示适当提示。
*   **存储管理**: 对于可能大量增长的数据（如聊天记录、图片缓存），需要考虑存储空间限制和清理策略。

## 3. 技术选型

根据 Flutter 生态和项目需求，推荐使用以下技术栈：

*   **安全存储**: `flutter_secure_storage`
    *   **用途**: 存储高度敏感的信息，如认证 `token`、`userId` 等。提供基于平台原生能力（Keychain/Keystore）的加密存储。
*   **键值对存储**: `shared_preferences`
    *   **用途**: 存储少量、简单的非敏感数据，如用户偏好设置 (`UserSettings`)、简单的应用状态标志（如是否首次启动、主题偏好）、临时草稿（如果结构简单）。读写性能较好，但不适合大量或结构化数据。
*   **本地数据库**: `drift` (原 Moor)
    *   **用途**: 存储结构化、关系型数据，是复杂缓存和离线数据存储的核心。适用于订单列表/详情、售后列表/详情、聊天会话/消息、商品目录缓存、卖家管理的商品/订单等。提供类型安全、响应式查询 (Streams) 和 SQL 能力。*（备选：`Isar`，一个 NoSQL 数据库，性能优异，但 API 风格不同）*
*   **文件存储**: `path_provider` + Dart `dart:io`
    *   **用途**: 存储较大的非结构化数据，如图库选择的待上传文件、复杂的草稿（如保存为 JSON 文件）、下载的附件等。需要配合 `path_provider` 获取应用可用的存储目录。
*   **内存缓存**: Dart `Map` 或自定义 Cache 类
    *   **用途**: 存储访问非常频繁、生命周期较短或易于失效的数据。例如，短时缓存用户信息、仪表盘数据、网络请求结果（配合 TTL）。需要自行管理缓存大小和失效逻辑。
*   **网络图片缓存**: `cached_network_image`
    *   **用途**: 自动处理网络图片的下载、缓存（内存和文件）和显示。适用于商品图片、用户头像、Banner 图片等。

## 4. 模块化策略详解

### 4.1. `Auth` (认证)

*   **Token/UserID**: 使用 `flutter_secure_storage` 存储。这是最高优先级，必须安全。
*   **认证状态 (简单标志)**: 可选地使用 `shared_preferences` 存储一个简单标志（如 `isAuthenticated=true/false`），用于快速判断是否需要显示登录页，但实际的认证状态判断应依赖 `flutter_secure_storage` 中 Token 的存在与否。
*   **`AuthenticatedUser`**: 登录成功后，`token` 和 `userId` 存入 `flutter_secure_storage`。其他用户信息（如有）不在此处存储，由 `Profile` 模块管理。

### 4.2. `Profile` (个人中心/用户资料)

*   **`UserProfile`**:
    *   **缓存**: 首次获取后，在 `UserRepositoryImpl` 中进行**内存缓存**，设置较短的 TTL（如 5-15 分钟）或在关键操作（如登出、手动刷新）后失效。
    *   **本地存储**: 可选地，将 `UserProfile` 存入 `drift` 数据库，用于离线时展示基本信息。
*   **`UserAddressList`**:
    *   **缓存**: 内存缓存（TTL 较短或操作后失效）。
    *   **本地存储**: 存入 `drift` 数据库，用于地址选择器快速加载和离线查看。
*   **`UserSettings`**:
    *   **本地存储**: 使用 `shared_preferences` 存储，因为通常是简单的键值对结构。

### 4.3. `Home` (首页)

*   **`HomePageData` (Banners, Categories, Initial Feed)**:
    *   **缓存**: 内存缓存，设置 TTL（如 5-30 分钟）。下拉刷新时强制从网络获取。
    *   **本地存储**: 可选地将 Banner 和 Category 数据存入 `drift`，用于离线时展示骨架或上次加载的内容。Feed Items 不建议默认持久化存储，除非有明确的离线阅读需求。
*   **图片**: 使用 `cached_network_image` 处理所有网络图片。

### 4.4. `Product` / `Item` (商品) - (*假设存在，基于其他模块的依赖推断*)

*   **`Product Detail`**:
    *   **缓存**: 内存缓存最近查看的几个商品详情，设置 TTL。
    *   **本地存储**: 核心商品信息（ID, 名称, 价格, 主图, 描述）可以存入 `drift` 数据库，作为商品目录缓存，用于离线展示或加速订单/购物车中的商品信息显示。需要定期同步或按需更新。
*   **图片**: 使用 `cached_network_image`。

### 4.5. `Cart` (购物车)

*   **`Cart` 状态**:
    *   **缓存**: 内存缓存。由于购物车状态变化频繁（加减商品、改数量），且对实时性要求高，主要依赖 API 获取最新状态。内存缓存可以减少连续快速访问时的网络请求。
    *   **本地存储**: **不推荐**默认实现离线购物车，因为价格、库存、促销等实时性强。如果业务强制要求离线购物车，则需使用 `drift` 存储，并设计复杂的同步和冲突解决机制。

### 4.6. `Orders` (订单)

*   **`OrderList` (分页)**:
    *   **缓存**: 内存缓存最近加载的几页数据。
    *   **本地存储**: 使用 `drift` 数据库存储订单列表 (`OrderSummary`) 数据。实现"缓存优先，网络回填"策略：优先从数据库加载数据显示，同时异步请求网络获取最新数据并更新数据库和 UI。按状态筛选可以直接查询数据库。
*   **`OrderDetail`**:
    *   **缓存**: 内存缓存最近查看的几个订单详情。
    *   **本地存储**: 使用 `drift` 数据库存储订单详情 (`Order`)。查看详情时，优先从数据库加载，后台请求网络更新。
*   **订单要求草稿**:
    *   **本地存储**: 使用 `shared_preferences`（如果结构简单，如纯文本）或**文件存储**（如果包含文件路径列表等复杂结构，保存为 JSON）。在 `OrderRequirementSubmissionForm` 中实现读写逻辑。

### 4.7. `AfterSale` (售后服务 / 退款)

*   **`AfterSaleApplication List`**:
    *   **缓存**: 内存缓存。
    *   **本地存储**: 类似订单列表，使用 `drift` 数据库存储，实现缓存优先策略。
*   **`AfterSaleApplication Detail`**:
    *   **缓存**: 内存缓存。
    *   **本地存储**: 类似订单详情，使用 `drift` 数据库存储。
*   **售后申请草稿 (如果需要)**: 类似订单要求草稿，使用 `shared_preferences` 或文件存储。

### 4.8. `Logistics` (物流 / 追踪)

*   **`TrackingInfo`**:
    *   **缓存**: 内存缓存，设置较短 TTL（如 5-15 分钟），因为物流状态会更新。
    *   **本地存储**: 可选地将最后一次获取的 `TrackingInfo` (包含 `events`) 存入 `drift`，用于离线查看上次的物流状态。

### 4.9. `Chat` (聊天)

*   **`ChatSession List`**:
    *   **本地存储**: 必须使用 `drift` 数据库存储会话列表。列表的更新（新消息、未读数）依赖实时消息推送和数据库更新。
*   **`ChatMessage History` (分页)**:
    *   **本地存储**: 必须使用 `drift` 数据库存储消息历史。按需分页从数据库加载。接收到的新消息实时写入数据库。
*   **待发送消息**: 临时状态（如 `sending`）可以在内存中管理，并存入数据库，发送成功/失败后更新数据库中的状态。
*   **图片/文件**: 上传前临时保存使用**文件存储**。接收到的图片 URL 使用 `cached_network_image` 展示。

### 4.10. `Rating` (评价 / 评论)

*   **评价草稿**:
    *   **本地存储**: 使用 `shared_preferences` 或文件存储（如果包含图片路径）保存未提交的评价内容。
*   **已提交评价 (查看)**:
    *   **缓存**: 内存缓存。
    *   **本地存储**: 可选地将商品/订单关联的评价存入 `drift`，用于离线查看或加速显示。

### 4.11. `Seller` (卖家中心)

*   **`SellerDashboardData`**:
    *   **缓存**: 内存缓存，设置 TTL（如 5-10 分钟），或在关键操作后失效。
*   **`SellerManagedProduct List/Detail`**: 类似用户侧的商品，使用 `drift` 进行本地存储和缓存。
*   **`SellerOrder List/Detail`**: 类似用户侧的订单，使用 `drift` 进行本地存储和缓存。
*   **`SellerStoreProfile`**: 类似 `UserProfile`，内存缓存 + 可选 `drift` 存储。
*   **卖家聊天**: 遵循 `Chat` 模块策略，数据存储在同一数据库，但通过 `Repository` 层进行数据隔离和过滤。

## 5. 缓存失效与同步策略

*   **TTL (Time-To-Live)**: 为内存缓存和部分数据库缓存（如商品目录）设置合理的过期时间。
*   **用户操作触发**: 登出时清除所有用户相关缓存和本地存储（`shared_preferences` 中可能保留少量非敏感设置）。执行修改操作（如更新地址、提交订单、发送消息）后，应主动失效或更新相关缓存/本地数据。
*   **下拉刷新/手动刷新**: 提供明确的用户操作来强制清除缓存并从网络获取最新数据。
*   **后台同步**: 对于重要离线数据（如聊天消息），应用启动时或网络恢复时，应有后台任务检查并同步未发送或未更新的数据。
*   **实时推送**: WebSocket 或其他推送服务是更新实时性要求高的数据（如新聊天消息、订单状态变更）的最佳方式。接收到推送后，应更新本地数据库和/或内存缓存，并通知 UI 刷新。

## 6. 未来考虑

*   **缓存大小管理**: 对于 `drift` 数据库和图片文件缓存，考虑设置存储上限和清理策略（如 LRU - 最近最少使用）。
*   **网络状态监控**: 结合 `connectivity_plus` 等插件，根据网络状态决定数据获取策略（在线时优先网络，离线时只读本地）。
*   **后台数据同步服务**: 对于复杂的同步需求，可能需要实现独立的后台服务（如使用 `workmanager`）。

通过实施此策略，项目可以在性能、用户体验和数据一致性之间取得良好平衡，并为后续的功能开发提供清晰的数据管理指导。
