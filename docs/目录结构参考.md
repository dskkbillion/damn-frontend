## 架构说明

### 项目结构说明

- **app/**: 存放应用的整体配置、启动逻辑、导航和全局依赖注入的设置。它负责把所有东西"组装"起来。
- **core/**: 存放那些会被多个功能模块共享的代码。这有助于代码复用，并保持功能模块的独立性。注意避免让 core 变得过于臃肿，只放真正通用的东西。
- **features/**: 这是项目的主体，每个子目录代表一个相对独立的功能模块。这是实现模块化和降低认知负担的关键。

### 模块内部结构 (features/xxx/)

- 严格遵循 **Clean Architecture** 分层:
  - **presentation**: 只包含 UI 展示和状态管理逻辑
  - **domain**: 包含纯粹的业务逻辑，不依赖任何外部框架（UI, Data）。这是模块的核心
  - **data**: 负责实现 Domain 层定义的接口，处理具体的数据来源和存储

### 依赖规则

- `features/xxx/presentation` 依赖 `features/xxx/domain`
- `features/xxx/data` 依赖 `features/xxx/domain`
- `features/xxx` 可以依赖 `core`
- 严禁 `features/xxx/domain` 依赖 presentation 或 data
- 尽量避免 `features/moduleA` 直接依赖 `features/moduleB` 的 presentation 或 data 层
- 模块间交互优先通过 Domain 层接口或共享的 core 服务进行

这个结构清晰地体现了 Clean Architecture 的分层思想，并通过 features 目录实现了业务模块化，有助于降低耦合度、提高可维护性和可测试性，非常适合你正在进行的重构项目。你可以根据项目的具体规模和复杂度，对这个基础结构进行微调。

## 核心层接口组织模式 (Core Layer Interface Organization Pattern)

为了构建松耦合、可测试、可维护的模块化 Flutter 应用，我们遵循 Clean Architecture 的原则，特别强调 **依赖倒置原则 (Dependency Inversion Principle - DIP)**。其中一个关键实践是在 `core` 层组织跨模块交互的接口（契约）。

### 模式描述

将定义模块间交互契约的抽象类或接口，放置在 `lib/core/` 目录下，并**按照提供该接口能力的领域或模块进行组织**。

**示例结构:**

```
lib/
├── core/
│   ├── auth/                    # 认证领域的核心接口
│   │   └── repositories/
│   │       └── i_auth_repository.dart
│   ├── navigation/              # 导航服务的核心接口
│   │   └── services/
│   │       └── i_navigation_service.dart
│   ├── aftersale/               # 售后领域的核心接口
│   │   └── repositories/
│   │       └── i_aftersale_repository.dart
│   ├── payment/                 # 支付领域的核心接口
│   │   └── services/
│   │       └── i_payment_service.dart
│   ├── rating/                  # 评价领域的核心接口
│   │   └── repositories/
│   │       └── i_rating_repository.dart
│   ├── logistics/               # 物流领域的核心接口
│   │   └── repositories/
│   │       └── i_logistics_repository.dart
│   └── ...                      # (其他核心领域/模块接口)
│
├── features/
│   ├── orders/                  # 订单模块
│   │   ├── domain/
│   │   │   └── usecases/
│   │   │       └── get_order_detail_use_case.dart // 依赖 IAuthRepository, IAfterSaleRepository 等
│   │   └── ...
│   ├── auth/                    # 认证模块
│   │   ├── data/
│   │   │   └── repositories/
│   │   │       └── auth_repository_impl.dart // 实现 IAuthRepository
│   │   └── ...
│   └── ...                      # (其他功能模块)
│
└── ...
```

### 目的与优势

1.  **依赖倒置:**
    *   高层模块（如 `features/orders`）不直接依赖低层模块（如 `features/auth` 的具体实现）。
    *   两者都依赖于 `core` 中定义的抽象接口 (`IAuthRepository`)。
    *   抽象不依赖细节，细节（`AuthRepositoryImpl`）依赖抽象。
2.  **解耦 (Decoupling):**
    *   模块间的依赖关系通过稳定的接口建立，降低耦合度。
    *   一个模块内部实现的变更，只要不违反接口契约，就不会影响依赖它的其他模块。
3.  **可测试性 (Testability):**
    *   依赖的是接口，非常容易在单元测试或 Widget 测试中使用 Mockito 等工具模拟（Mock）外部依赖，实现模块的隔离测试。
4.  **可维护性 (Maintainability):**
    *   代码结构更清晰，职责更分明。修改和维护时影响范围更可控。
5.  **并行开发 (Parallel Development):**
    *   一旦接口定义完成，不同模块可以基于共同的契约并行开发。依赖方可以使用 Mock 实现进行开发，直到提供方实现完成。
6.  **清晰的契约:**
    *   接口明确定义了模块间交互的方式、输入和输出，便于协作和对接。

### 如何实践

1.  **识别依赖:** 当一个功能模块（如 `Orders`）需要调用另一个模块（如 `Auth`）或核心服务（如 `Navigation`）的功能时，识别出这种跨模块依赖。
2.  **定义接口:** 在 `lib/core/` 下，为**提供方**领域创建一个目录（如 `auth/`），并在其中定义相应的接口（如 `repositories/i_auth_repository.dart`）。接口应只包含调用方需要的方法和数据结构。
3.  **依赖接口:** 在**调用方**模块（如 `Orders` 的 Use Case 或 Bloc/Cubit）中，通过构造函数注入或服务定位器获取 `core` 中定义的**接口**，而不是具体实现。
4.  **实现接口:** 在**提供方**模块（如 `Auth`）的 `data` 层（通常是 `repositories` 子目录）创建实现该接口的具体类（如 `auth_repository_impl.dart`）。
5.  **依赖注入 (DI):** 使用依赖注入容器（如 GetIt, Provider）在应用启动或模块初始化时，将接口与其具体实现进行绑定。这样当调用方请求接口时，DI 容器会提供相应的实例。

### 对比：直接依赖实现

直接让 `Orders` 模块依赖 `Auth` 模块的具体类（如 `AuthRepositoryImpl`），会导致：

*   **紧耦合:** `Auth` 内部实现变化可能迫使 `Orders` 修改。
*   **测试困难:** 难以 Mock 依赖，无法有效进行隔离测试。
*   **维护复杂:** 依赖关系混乱，修改容易引发连锁反应。
*   **合并冲突:** 直接修改 `core` 或 `feature` 模块间的具体类更容易在合并时产生冲突。

**因此，强烈推荐遵循在 `core` 层按模块/领域组织接口的模式。**
